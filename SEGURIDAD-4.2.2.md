# SISFIA 4.2.2 — Seguridad, respaldo y recuperación

## Alcance comprobado
Base: ZIP 4.2.1. Se conservan todos los módulos y no se altera el esquema de las tablas financieras. Las nuevas escrituras de tesorería requieren PAYROLL_DATA_KEY válida: cifrado AES-256-GCM del JSON, AAD con empresa/tipo/mes/cuenta, cuenta de índice seudonimizada con HMAC. Las lecturas anteriores siguen disponibles. No se cifran retrospectivamente por el mero despliegue. Los IDs, fechas, importes, revisiones y vínculos se conservan. El nombre del archivo, banco, periodo y otros metadatos siguen visibles en la DB. La evidencia de conciliación y la comparación de planillas leen ambos formatos. El respaldo web ya no permite texto claro y exige MFA y desbloqueo reciente de Planillas. El respaldo web sigue siendo un respaldo lógico por institución, no un respaldo completo de infraestructura. Se añaden registros de consulta de tesorería y se evitan detalles internos de fallos del lector documental. Los usuarios autorizados siguen pudiendo consultar los datos y descargar informes según permisos existentes.

## Actualización segura
1. Antes de desplegar, haz un respaldo verificable con Turso o con el procedimiento completo de abajo. Prueba en un entorno separado. Conserva el ZIP anterior y la configuración. Si el repositorio aún está en una versión anterior a 4.2.1, utiliza los bloques completos.
2. Conserva exactamente PAYROLL_DATA_KEY. Si nunca se configuró, genera 32 bytes aleatorios Base64 (no usar una contraseña humana) y guárdalos offline. No se exige cambiar JWT_SECRET. Al instalar 4.2.2 no configures aún SISFIA_ENCRYPTION_KEY si no lo usabas. No publiques secretos en GitHub.
3. Despliega. Comprueba inicio de sesión, MFA, consulta de datos, importación ficticia, totales, exportaciones, y verifica que el respaldo web requiere desbloquear Planillas desde Seguridad. El arranque verifica una muestra de registros cifrados por tipo/versión; si falla, revisa las claves originales. No reemplaces claves al azar.
4. No cargues planillas reales nuevas hasta aprobar pruebas dinámicas y revisión independiente.

## Respaldo completo (ejecución en equipo privado externo)
Con Node 22, dependencias instaladas, una base inicializada, acceso autorizado a Turso (preferentemente token de lectura) y entorno privado. Genera una clave SISFIA_BACKUP_KEY independiente de 32 bytes Base64, conserva copia offline y guarda las credenciales en el gestor de secretos del equipo, no en argumentos de comandos ni en GitHub. Configura TURSO_DATABASE_URL/TURSO_AUTH_TOKEN de forma segura. Si trabajas con una base local existente configura DB_PATH. Ejecuta desde la raíz del proyecto:

```
node scripts/full-backup.js /ruta/privada/respaldo.json
node scripts/restore-full-backup.js /ruta/privada/respaldo.json
node scripts/restore-full-backup.js /ruta/privada/respaldo.json /ruta/privada/prueba-nueva.db
```

El primero obtiene una instantánea de lectura lógica de 20 tablas persistentes, incluidas cuentas, permisos, auditoría, MFA y planillas cifradas, con recuentos y secuencias. No guarda sesiones ni intentos de autenticación, variables de entorno, secretos externos, archivos originales ni historial interno del proveedor. El segundo autentica el respaldo y muestra recuentos. El tercero crea una base SQLite local nueva, nunca sobrescribe una existente ni escribe en Turso. Comprueba integridad referencial y recuentos. El respaldo puede requerir memoria proporcional a la base; verificar límites y retención con datos de prueba. Conserva también todas las claves necesarias para abrir el cifrado interno; la clave del respaldo por sí sola no descifra planillas ya cifradas. La restauración es un ensayo local, no un procedimiento certificado de recuperación del proveedor. Protege el equipo y elimina el archivo de prueba de acuerdo con la política institucional.

Para automatizar diariamente en un host Linux privado: configura SISFIA_BACKUP_DIR absoluto en el entorno seguro del proceso y programa `scripts/backup-daily.sh` mediante cron o systemd con los secretos cargados de forma segura. El script usa bloqueo de concurrencia, archivos con permisos restrictivos, y verifica el cifrado. Configura copia externa, retención, alertas de fallo y restauración periódica. No programa ni crea por sí solo un servicio remoto. No uses el disco efímero de Render como único destino. No almacenes backups en repositorios ni artefactos CI.

## Cifrar tesorería histórica
En entorno de prueba primero. Detén todos los escritores de la base, realiza respaldo y prueba su restauración. Ejecuta `node scripts/protect-storage.js` (solo simulación; muestra recuentos). Si no hay inconsistencias y se cuenta con autorización, define SISFIA_MAINTENANCE_CONFIRMED=YES en el proceso privado y ejecuta `node scripts/protect-storage.js --apply`. La operación usa una transacción y detecta posibles colisiones de cuenta/periodo. Es idempotente, no crea operaciones financieras. Si hay un documento excesivo o un límite de Turso, la transacción falla; no se debe continuar sin revisar. El contenido histórico en copias, WAL, logs, snapshots del proveedor y exportaciones previas puede seguir en claro; este cambio no garantiza borrado físico.

## Rotación de clave de almacenamiento
Mantén PAYROLL_DATA_KEY original, que sigue siendo la clave estable de identificación (HMAC) y lectura de cifrados v1/respaldos antiguos. La nueva clave rotatoria SISFIA_ENCRYPTION_KEY cifra el almacenamiento v2, no cambia códigos de trabajadores o cuentas. Rotar la clave original de identidad ante una exposición requiere un proyecto separado. Con el servicio detenido, respaldo verificado y claves anteriores disponibles, configura SISFIA_NEXT_ENCRYPTION_KEY con una clave independiente y distinta. Ejecuta `node scripts/protect-storage.js --rotate` para simular, y solo tras validar `node scripts/protect-storage.js --rotate --apply` con SISFIA_MAINTENANCE_CONFIRMED=YES. Se recifran documentos bancarios/cobranza, planillas, versiones de planilla y MFA; se revocan sesiones. Después de confirmar commit, configura SISFIA_ENCRYPTION_KEY con la nueva clave antes de reiniciar y retira NEXT del entorno. Si el estado de commit es incierto no reinicies ni repitas sin verificar. Conserva claves antiguas offline para restaurar respaldos antiguos. Verifica acceso, MFA e historial. No retrocedas a una versión anterior que no pueda leer el formato cifrado. Un rollback de código requiere restauración compatible, no simple redeploy anterior.
